**Date**: 2026-05-06

## Context & What Was Discovered

### Performance Bottlenecks (Specific)
1. **Event loop blocking**: All API routes are `async def` but call synchronous `neo4j_handler` directly — no `run_in_executor`. Every query blocks the event loop.
2. **N+1 writes**: `update_entity` → sync `neo4j_handler.update_person()` → 1 DELETE + 1 CREATE per field = 40 queries for 20-field entity. Async batch version exists but isn't wired to routes.
3. **Missing pagination**: `list_entities` calls `get_all_people()` returning ALL entities. `get_all_people_paginated()` already exists in `neo4j_handler.py` — just not used.
4. **Unused cache**: `cache_service.py` and `query_cache.py` are fully built but wired to nothing on hot paths.
5. **Full table scan search**: Fallback search loads ALL entities into Python, `JSON.stringify`s every profile, runs `.includes()`. No debounce.
6. **Frontend**: `renderPeopleList()` rebuilds entire DOM on every keypress. `JSON.stringify` on every filter call. No virtual scroll.
7. **`get_all_relationships()`**: Loads entire project entity set into Python to find Neo4j relationships stored as serialized profile data — not native graph edges.
8. **Analytics**: Community detection, centrality, clustering all load full project into Python. Neo4j GDS would do these server-side.

### LaTeX Reporting
- Reports are currently Markdown files on disk (no charts, no PDF)
- `ReportStorageService` already has `ReportFormat.pdf` enum (placeholder)
- `weasyprint` is commented out in requirements.txt — HTML-to-PDF path exists but disabled
- No matplotlib, plotly, or LaTeX in dependencies

### Monitoring
- No Prometheus, structlog, OpenTelemetry, or Sentry in dependencies
- Standard library `logging` only
- Health endpoint exists at `/health` returning `{"status": "healthy"}`
- No request timing middleware

### Analytics Architecture
- Lightweight analytics exist inline in `graph_analytics.py` (Louvain, PageRank, etc. computed in Python)
- Heavy ML services archived in `archive/out-of-scope-ml/` (TF-IDF, ML clustering)
- User wants optional/modular analytics that can be turned on/off

### Deployment
- Docker Compose services: nginx, neo4j, redis, basset_api, celery_worker, celery_beat
- No deployment tests exist; only test_docker_network.sh shell script
- `tests/conftest.py` has good mock fixtures for unit tests

## Work Streams (Phase 2)

### Stream A: Performance Optimization

**A1 — Wire Existing Cache to Hot Paths**

Files to modify:
- `api/routers/entities.py` — wrap `get_all_people` with cache check/set
- `api/services/cache_service.py` — confirm `get_entity_list()` works for project+paginated key
- `neo4j_handler.py` — no changes needed; cache wraps at router layer

Cache strategy:
- Entity list: cache for 30s, invalidate on create/update/delete
- Entity detail: cache for 60s, invalidate on update/delete
- Cache key: `entity_list:{project_safe_name}:{page}:{limit}`

**A2 — Pagination (list_entities endpoint + frontend)**

Backend (`api/routers/entities.py`):
- Switch from `get_all_people()` to `get_all_people_paginated(page, limit)` — already exists in `neo4j_handler.py`
- Add query params: `page: int = 1`, `limit: int = 50`
- Return `{entities: [...], total: N, page: N, pages: N, has_next: bool}`

Frontend (`static/js/ui-people-list.js`):
- Add pagination state (`currentPage`, `pageSize=50`)
- Add "Load more" button or infinite scroll (Intersection Observer)
- Debounce search input: 300ms `setTimeout` before `filterPeople()`
- Stop using `JSON.stringify` for search — only search `name`, `email`, `phone` fields directly

**A3 — Fix N+1 Entity Update Writes**

Files to modify:
- `api/routers/entities.py` `update_entity` — switch from sync `neo4j_handler.update_person()` to async `AsyncNeo4jService.update_person()` using `set_person_fields_batch()` (UNWIND)
- Wrap with `asyncio.get_event_loop().run_in_executor(None, sync_fn)` for any remaining sync calls

**A4 — Fix Search Fallback**

Files to modify:
- `api/services/search_service.py` — add project scoping to partial match query; add `@cached_query` decorator; wrap fallback in async
- `api/services/suggestion_service.py` — batch DataItem queries instead of N+1 loop

**A5 — Fix Relationships Storage (Major)**

Currently `get_all_relationships()` loads ALL entity profiles and parses Python-side to find relationships.

Fix:
- Migrate to native Neo4j `RELATIONSHIP` edges (they already exist: `neo4j_handler` has `tag_person` creating `[:TAGGED]` relationships)
- `get_all_relationships()` should query `MATCH (a:Person)-[r:TAGGED]->(b:Person)` instead of loading all profiles
- Update test fixtures accordingly

### Stream C: LaTeX PDF Reporting

**Philosophy**: Use Jinja2 templates to generate `.tex` files, compile with `pdflatex` inside Docker. Charts generated with `matplotlib` and embedded as PDF figures. User can download the final PDF.

**Dockerfile changes**:
```dockerfile
# Add to production stage
RUN apt-get install -y \
    texlive-latex-base \
    texlive-latex-extra \
    texlive-fonts-recommended \
    texlive-pictures \
    latexmk
```

**Requirements to add**: `matplotlib>=3.9.0`, `pylatex>=1.4.2`

**New files**:
```
api/
  services/
    latex_report_service.py       ← Core PDF generation engine
  routers/
    reports_latex.py              ← New endpoints for LaTeX reports
  templates/latex/                ← Jinja2-based .tex templates
    base.tex.j2                   ← Base document template
    entity_profile.tex.j2         ← Single entity full report
    investigation_summary.tex.j2  ← Multi-entity investigation brief
    relationship_map.tex.j2       ← Graph analysis + diagram
    timeline.tex.j2               ← Timeline visualization
  utils/
    chart_generator.py            ← matplotlib chart rendering
```

**`latex_report_service.py`**:
```python
class LatexReportService:
    def generate_entity_profile_pdf(project_id, entity_id) -> bytes
    def generate_investigation_pdf(project_id, entity_ids) -> bytes
    def generate_relationship_report(project_id, entity_id, depth) -> bytes
    def generate_timeline_report(project_id, entity_id) -> bytes
    def _render_template(template_name, context) -> str  # .tex string
    def _compile_latex(tex_content) -> bytes  # pdflatex → PDF bytes
    def _cleanup_temp(tempdir)
```

**`chart_generator.py`** using matplotlib:
- `relationship_chart(entities, relationships)` → network graph image (NetworkX + matplotlib)
- `timeline_chart(events)` → horizontal timeline image
- `distribution_chart(entity_types)` → pie/bar chart of entity type distribution
- `activity_heatmap(activity_data)` → heatmap of investigation activity

**New API endpoints** (`api/routers/reports_latex.py`):
- `POST /api/v1/projects/{name}/reports/pdf/entity/{entity_id}` — entity profile PDF
- `POST /api/v1/projects/{name}/reports/pdf/investigation` — full investigation PDF  
- `POST /api/v1/projects/{name}/reports/pdf/relationships/{entity_id}` — relationship map PDF
- `POST /api/v1/projects/{name}/reports/pdf/timeline/{entity_id}` — timeline PDF
- All return: `{"status": "generating", "job_id": "..."}` (async via Celery) OR direct bytes stream

**Frontend addition** (`static/js/report-handler.js`):
- "Download PDF" button in entity detail panel → calls API
- Show progress spinner while generating
- Auto-download when complete

**LaTeX template features** (via `\usepackage{...}`):

- `pgfplots` — charts (alternative to embedding matplotlib images)

- `multirow` — merged table cells

**Goal**: Research and document a modular analytics architecture. No implementation yet — discovery mode.

**Research questions**:

2. What does NetworkX offer that our inline Python analytics don't?
3. What does the archived `ml_analytics_service.py` do that could be revived?
4. What analytics features would OSINT investigators actually find valuable?

**Deliverables**:
- `docs/findings/ANALYTICS-ARCHITECTURE-2026-05-06.md` — full research document
- `docs/findings/ANALYTICS-PLUGIN-DESIGN.md` — plugin architecture spec

**Plugin Architecture Design**:
```
basset-hound/
  api/
    analytics/                    ← New analytics plugin system
      __init__.py                 ← Plugin registry + feature flags
      base_plugin.py              ← Abstract base class for analytics plugins
      core/                       ← Always-on lightweight analytics
        basic_graph.py            ← Degree, paths, simple clustering (no dependencies)
        basic_search.py           ← Basic matching (already exists)
      optional/                   ← Feature-flagged heavy analytics
        graph_ml.py               ← NetworkX/sklearn-based ML (flag: ENABLE_ML_ANALYTICS)
        temporal.py               ← Time-series pattern detection
        community.py              ← Advanced community detection
        predictions.py            ← Link prediction
```

Feature flag via env vars:
```
ENABLE_BASIC_ANALYTICS=true      (default: true)
ENABLE_ML_ANALYTICS=false        (default: false, requires heavy deps)
ENABLE_GDS_ANALYTICS=false       (default: false, requires Neo4j Enterprise)
```

**Docker profile-based deployment**:
```yaml

  basset_api:
    profiles: ["core", "full"]

    profiles: ["full"]
```
