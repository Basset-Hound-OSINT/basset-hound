## 3. Architecture Decisions & Reasoning

### Frontend Architecture: Modular Component Approach

**Decision**: Use React components with TypeScript, bundled as UMD/ES modules, embedded in vanilla JS dashboard

**Rationale**:
1. **Reusability**: React components (SuggestionPanel, etc.) can be used in multiple contexts
2. **Type Safety**: TypeScript provides compile-time error checking
3. **Build Optimization**: Separate bundles for suggestions reduce main app size
4. **Graceful Degradation**: If React fails, vanilla JS fallback still functions
5. **Team Familiarity**: Modern web stack aligns with developer expectations

**Trade-offs Accepted**:
- Bundle size slightly larger (39KB UMD + 60KB ES)
- External React dependency required
- Browser compatibility requires ES5 transpilation

### Real-Time Architecture: WebSocket for Suggestions

**Decision**: Use WebSocket (ws://localhost:8080/ws/suggestions/{projectId}) for real-time updates

**Rationale**:
1. **Low Latency**: Suggestions appear immediately when new matches are found
2. **Bi-directional**: Server can push updates without client polling
3. **Resource Efficient**: Single persistent connection vs HTTP polling overhead
4. **Scalable**: Supports multiple concurrent projects
5. **User Experience**: Badge count updates in real-time without page refresh

**Implementation Details**:
- FastAPI WebSocketManager handles connections per project
- Broadcast on suggestion creation/update/dismiss
- Automatic reconnection on disconnection
- Heartbeat keep-alive (30s intervals)

### Styling Framework: Bootstrap 5.3 + Custom CSS

**Decision**: Use Bootstrap 5.3 for responsive grid/components, custom CSS for application-specific styling

**Rationale**:
1. **Rapid Development**: Pre-built components (buttons, modals, navs, alerts)
2. **Responsive by Default**: Mobile-first design automatically responsive
3. **Consistency**: Unified color scheme and typography
4. **Accessibility**: Built-in WCAG compliance and keyboard support
5. **Custom Override**: CSS variables allow easy theming

**Custom CSS Files**:
- `static/css/dashboard.css` → Main dashboard styling
- `static/css/map-controls.css` → Graph controls panel
- `static/css/suggestions.css` → Suggestions panel styling

### Graph Visualization: Cytoscape.js

**Decision**: Use Cytoscape.js for graph visualization instead of D3.js or Vis.js

**Rationale**:
1. **Neo4j Native**: Direct integration with Neo4j graph data structure
2. **Performance**: Efficient rendering for 100+ nodes with 500+ edges
3. **Layout Algorithms**: Built-in COSE, Breadthfirst, Circle, Grid layouts
4. **Styling**: CSS-like selectors for node/edge styling
5. **Interactivity**: Native click, drag, zoom, pan handlers
6. **Export**: GraphML export for external tools

**Layout Performance**:
- Force-directed (COSE): <1s for 100 nodes
- Breadthfirst: <500ms for hierarchical data
- Circle/Grid: <100ms (simple calculation)

### Testing Strategy: Separate Integration & Unit Tests

**Decision**: Maintain separate test files for unit tests (stateless) and integration tests (with DB)

**Rationale**:
1. **Speed**: Unit tests run in milliseconds without DB overhead
2. **Isolation**: Integration tests don't interfere with CI/CD unit test speed
3. **Debugging**: Failed unit tests immediately identify code issues
4. **Coverage**: Both fast feedback (units) and realistic scenarios (integration)
5. **CI/CD**: Fast unit tests run on every commit, integration tests run on PR

**Test File Organization**:
```
tests/
├── unit/                    # Fast, no DB, pytest fixtures
│   ├── test_*.py           # Individual module tests
├── integration/            # With Neo4j DB, docker services
│   ├── test_*.py           # Feature integration tests
├── deployment/             # Full docker-compose validation
│   ├── test_*.py           # Fresh deployment E2E tests
```

### Error Handling Strategies

**Backend** (`api/`):
1. **Custom Exceptions**: `EntityNotFound`, `InvalidRelationship`, `MergeConflict`
2. **HTTP Error Responses**: Proper status codes (400, 404, 409, 500)
3. **Error Details**: Include error message, error code, suggestion field in response
4. **Logging**: Structlog JSON output with request ID for tracing
5. **Graceful Degradation**: Cache misses fall through to DB, WebSocket disconnections auto-reconnect

**Frontend** (`static/js/`, React components):
1. **Try-Catch Blocks**: Wrap API calls and state updates
2. **Error Boundaries**: React error boundaries catch component rendering errors
3. **Toast Notifications**: User-facing error messages via Bootstrap alerts
4. **Console Logging**: Development debugging with structured logs
5. **Fallback UI**: Show "retry" button if suggestion fetch fails
6. **Timeout Handling**: 10s timeout on API calls with "Connection lost" message

**Database** (Neo4j):
1. **Transaction Rollback**: Failed operations don't partially write
2. **Constraint Enforcement**: Unique constraints prevent duplicate entities
3. **Index Usage**: Query optimization prevents timeout on large graphs
4. **Connection Pooling**: 10-20 connections with 30s keep-alive

### WebSocket Integration Details (Stream 3)

**Connection Lifecycle**:
```javascript
// 1. User selects entity
entity-selected event → onEntitySelected()

// 2. Subscribe to suggestions
ws = new WebSocket("ws://localhost:8080/ws/suggestions/projectId")
ws.onopen = () => emit('subscribed', { entityId })

// 3. Receive real-time updates
ws.onmessage = (event) => {
  suggestions = JSON.parse(event.data)
  updateBadgeCount(suggestions.length)
  updateSuggestionsPanel(suggestions)
}

// 4. Send user actions
dismissSuggestion(id) → POST /api/v1/suggestions/{id}/dismiss
mergeEntities(source, target) → POST /api/v1/suggestions/linking/merge-entities

// 5. Cleanup on unmount
ws.close()
```

**Heartbeat Protocol** (Keep-Alive):
```
Client: PING (30s intervals)
Server: PONG
Server closes if no PING for 60s (client reconnects)
```

## 6. Known Issues & Blockers

### Outstanding Issues (Minor)

1. **Graph Visualization - Large Graphs (100+ nodes)**
   - **Issue**: COSE layout takes >1.5s for 100+ node graphs
   - **Impact**: User sees delay before layout completes
   - **Workaround**: Switch to Circle or Grid layout for faster rendering
   - **Solution**: Implement background layout computation for next session

2. **WebSocket Reconnection**
   - **Issue**: If WebSocket disconnects, auto-reconnect takes up to 30s
   - **Impact**: User may miss real-time suggestion updates briefly
   - **Workaround**: Manual refresh loads latest suggestions
   - **Solution**: Reduce reconnect timeout to 5s, add exponential backoff

3. **PDF Generation - Complex Graphs**
   - **Issue**: PDF generation with 50+ relationships times out at 5s
   - **Impact**: Large entity profiles may fail to generate PDF
   - **Workaround**: Generate PDF without embedded graph, link separately
   - **Solution**: Implement async PDF generation in background task

4. **Suggestion ML Algorithm**
   - **Issue**: False positive matches for common names (e.g., "John Smith")
   - **Impact**: Users may see irrelevant suggestions
   - **Workaround**: Increase confidence threshold to 0.85+ or manually dismiss
   - **Solution**: Implement additional fuzzy matching rules with entity type weighting

## 11. Decisions Made & Rationale

### Architectural Decisions

#### 1. Modular Frontend Components Over Monolithic SPA
**Decision**: Bundle React components separately (suggestions, graph, etc.) rather than single large React app

**Why**:
- Incremental adoption: Can use React components in vanilla JS dashboard
- Bundle size: Smaller total JS download
- Flexibility: Easy to swap components or use different frameworks

**Trade-off**: Slightly more complex build process

---

#### 2. WebSocket for Real-Time Updates Over HTTP Polling
**Decision**: Use WebSocket (ws://) for suggestions and entity change notifications

**Decision**: Use Neo4j 5.x with GDS plugin for relationship storage

- **Flexible schema**: Can add new relationship types without migration

### Data Modeling Decisions

#### 1. Entity Types as Properties, Not Inheritance
**Decision**: Store entity type as string property, not Neo4j node labels

**Why**:
- **Flexibility**: Add new types without schema migration
- **Simplicity**: No multi-label complexity
- **Queryability**: Simple WHERE clauses

**Trade-off**: Can't use label-based optimization in queries

```cypher
# USED: Entity with property
MATCH (e:Entity {entity_type: 'Person'})

# NOT USED: Multiple labels (more complex)
MATCH (e:Person:Entity)
```

---

#### 2. Relationships as Neo4j Edges With Properties
**Decision**: Store relationship metadata (confidence, created_by, etc.) as relationship properties

**Why**:
- **Neo4j native**: Designed for property-rich relationships
- **Efficient**: No extra nodes for metadata
- **Queryable**: Can filter by relationship properties

**Trade-off**: Can't use property keys for complex metadata without serialization

```cypher
# USED: Relationship with properties
(person)-[knows:KNOWS {confidence: 0.92, since: '2020-01-01'}]->(person)

# NOT USED: Separate metadata node
(person)-[knows:KNOWS]->(metadata:RelationshipMetadata)-[has:HAS_METADATA]->(person)
```

---

#### 3. Account as Relationship, Not Entity
**Decision**: Model social media accounts as HAS_ACCOUNT_ON relationships between Person/Org and Platform

**Why**:
- **Ontological correctness**: Accounts are inherently relational
- **Efficiency**: No extra entity node
- **Natural queries**: Find all accounts: (p)-[:HAS_ACCOUNT_ON]->(platform)

**Trade-off**: Less flexible if account properties become complex

```cypher
# USED: Account as relationship
(person:Entity)-[has:HAS_ACCOUNT_ON {username: '@john_doe'}]->(platform:Platform)

# NOT USED: Account as entity
(person)-[has:HAS_ACCOUNT]->(account:Account)-[on:ON]->(platform)
```
